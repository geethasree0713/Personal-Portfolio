Firebase Authentication, Explained: Login Without Building It Yourself

Firebase Authentication handles the entire login system for you — email/password, Google, phone OTP, and more — so you never touch passwords directly. Here's how it actually works, step by step.

What Is Firebase Authentication?

Firebase Authentication is a ready-made login system from Google. Instead of writing your own code to store passwords, hash them, verify emails, and manage sessions, you plug in Firebase and it does all of that for you — securely, and for free up to a generous usage limit.

It supports several ways for a user to sign in, called providers:

  • Email and password
  • Google, Facebook, GitHub, Apple (social sign-in)
  • Phone number (OTP via SMS)
  • Anonymous (guest) accounts

You don't build any of these flows from scratch — Firebase gives you a small SDK function call for each one.

How It Works, Step by Step

  • 1. Set up a project — Create a project in the Firebase console and enable the sign-in methods you want (e.g. Email/Password, Google).
  • 2. Add the SDK — Install firebase in your app and initialize it with your project's config keys.
  • 3. User signs up or logs in — Your app calls a Firebase function like createUserWithEmailAndPassword() or signInWithPopup().
  • 4. Firebase handles the heavy lifting — It checks credentials (or runs the Google/social login popup), creates the user record, and returns a signed-in user object.
  • 5. Firebase issues an ID token — Behind the scenes, this is a JWT that proves who the user is. Firebase auto-refreshes it so you rarely think about it.
  • 6. Your backend verifies the token — If you have your own server, it uses the Firebase Admin SDK to verify the ID token on incoming requests, so it knows which user is calling.

A minimal example (email/password sign-in)

import { getAuth, signInWithEmailAndPassword } from "firebase/auth";

const auth = getAuth();

signInWithEmailAndPassword(auth, email, password)
  .then((userCredential) => {
    const user = userCredential.user;
    console.log("Signed in as", user.uid);
  })
  .catch((error) => {
    console.log(error.code, error.message);
  });

That's the whole client-side login flow. No password hashing, no session table, no "forgot password" email logic to write yourself — Firebase has built-in functions for all of it.

Where the JWT Fits In

Firebase Authentication actually uses JWTs internally. Once a user signs in, Firebase gives your app an ID token — a signed JWT containing the user's UID, email, and expiry time. If you've already understood plain JWT auth, Firebase Auth is really "JWT auth, pre-built for you," with Google's servers doing the signing and verification instead of your own backend. 

const idToken = await auth.currentUser.getIdToken();
// send idToken to your backend as: Authorization: Bearer <idToken>

Your backend then verifies that token using the Firebase Admin SDK instead of checking a signature manually.

Firebase Auth vs Rolling Your Own JWT Auth

Firebase AuthenticationCustom JWT Auth
No backend required to get startedYou build and maintain your own auth server
Social/phone login built inYou'd have to integrate each provider yourself
Password reset, email verification includedYou write and secure these flows yourself
Less control over token structure/claimsFull control over what goes in the token
Tied to Google's infrastructureYou own and can move your infrastructure freely

For most portfolio projects, side projects, and MVPs, Firebase Auth is the faster and safer choice — you're not the one responsible for storing passwords correctly. For large production systems with very specific auth requirements, teams often move to a custom JWT setup.

Common Pitfalls

1. Trusting the client-side user object blindly
Anyone can call Firebase client SDK functions from the browser. Never trust user.uid sent directly from the frontend for sensitive actions — always verify the ID token on your backend first.

2. Forgetting to refresh the token
ID tokens expire after an hour. The SDK auto-refreshes them for you in most cases, but if you're manually caching a token, it can go stale and get rejected by your backend.

3. Exposing Firebase config keys and assuming that's a risk
Firebase's client config (API key, project ID, etc.) is meant to be public — it's not a secret. The real security boundary is your Firestore/Database security rules and backend token verification, not hiding the config.

4. Skipping security rules
Authentication only proves who someone is — it doesn't automatically restrict what they can access. You still need Firestore/Storage security rules to control what each signed-in user can read or write.

Wrapping Up

Firebase Authentication is a great option when you want a working, secure login system fast without building password storage, token signing, and social login flows from scratch. Under the hood it's still JWT-based — Firebase just handles the signing, verification, and provider integrations for you.

If you already understand plain JWT auth (see my previous post), Firebase Auth will feel familiar — it's the same core idea, just managed for you.
