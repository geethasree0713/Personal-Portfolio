JWT Authentication, Explained: How It Works and Why It's Everywhere

If you've built or used any modern web app, chances are it's using JWT somewhere under the hood. Here's what it actually is, how the auth flow works end-to-end, and the mistakes that trip up almost everyone the first time they implement it.

What Is a JWT?

A JWT (JSON Web Token) is a compact, URL-safe string that represents a set of claims — pieces of information about a user or session — in a way that can be verified and trusted, because it's digitally signed.

A JWT looks like this:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiIxMjMiLCJyb2xlIjoiYWRtaW4ifQ.4f8a2b91c3d...

That's three Base64URL-encoded parts joined by dots:

header.payload.signature

1. Header

Specifies the token type and the signing algorithm used.

{
  "alg": "HS256",
  "typ": "JWT"
}

2. Payload

Contains the claims — the actual data. Common claims include:

{
  "userId": "123",
  "role": "admin",
  "iat": 1690000000,
  "exp": 1690003600
}
  • iat — issued at
  • exp — expiry time

Important: the payload is only Base64-encoded, not encrypted. Anyone can decode it and read it. Never put passwords, secrets, or sensitive personal data in a JWT payload.

3. Signature

This is what makes the token trustworthy. The server signs the encoded header + payload using a secret key (for HMAC algorithms like HS256) or a private key (for RSA/ECDSA algorithms like RS256): 

signature = HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

If anyone tampers with the payload — say, changing "role": "user" to "role": "admin" — the signature won't match anymore when the server verifies it, and the token gets rejected.

The Authentication Flow

Here's how JWTs are typically used in a login system:

  • Login — The user submits credentials (email/password) to the server.
  • Verification — The server checks the credentials against the database.
  • Token Issuance — If valid, the server creates a JWT containing the user's identity and signs it with a secret key.
  • Client Storage — The client stores the token (in an httpOnly cookie, or localStorage — more on this below).
  • Authenticated Requests — For every subsequent request, the client sends the token in the Authorization header.
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Verification on Server — the server verifies the token's signature and expiry on each request. No database lookup is needed to confirm the user is who they say they are — that's what makes JWT authentication stateless.

Why Stateless Matters

With traditional session-based auth, the server stores session data (usually in memory or a database) and the client just holds a session ID. Every request means a lookup.

With JWTs, all the necessary info is in the token itself. The server doesn't need to store anything — it just verifies the signature. This makes JWTs a natural fit for:

  • Microservices (any service with the secret key can verify the token independently)
  • APIs consumed by mobile apps and SPAs
  • Horizontally scaled systems (no shared session store needed)

Access Tokens vs Refresh Tokens

A common pattern — and one worth mentioning if you're describing a real implementation — is splitting tokens into two types:

Token TypeLifespanPurpose
Access TokenShort (minutes)Sent with every API request
Refresh TokenLong (days/weeks)Used only to get a new access token

This limits the damage if an access token is stolen — it expires quickly — while the refresh token (stored more securely, often in an httpOnly cookie) lets the user stay logged in without re-entering credentials constantly.

Common Pitfalls

1. Storing tokens in localStorage
localStorage is accessible via JavaScript, which makes it vulnerable to XSS attacks. If an attacker injects a malicious script, they can read the token directly. httpOnly cookies are safer since JavaScript can't access them — though they bring their own consideration (CSRF), which needs separate protection like CSRF tokens or SameSite cookie attributes.

2. Treating the payload as private
Since the payload is just Base64-encoded, not encrypted, anyone can decode it (try pasting a JWT into jwt.io). Never store passwords, SSNs, or other sensitive data in the payload.

3. No revocation strategy
Because JWTs are stateless, there's no built-in way to "log out" a token before it expires — the server isn't tracking active tokens. Common workarounds: short expiry times, token blacklists/denylists in a cache like Redis, or rotating refresh tokens.

4. Weak or hardcoded secrets
The whole security model rests on the signing secret staying private. A weak or leaked secret means anyone can forge valid tokens.

Wrapping Up

JWT authentication is popular because it's simple, stateless, and scales cleanly — but that simplicity hides a few sharp edges: where you store the token, how long it lives, and what happens when it needs to be revoked early. Understanding these trade-offs is what separates "I used JWT" from "I understand why JWT was the right (or wrong) choice here."
